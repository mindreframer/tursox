# ADR 002: Reuse warm BEAM peers for multiprocess tests

- Status: accepted
- Scope: ExUnit multiprocess-WAL verification
- Dependency: DevCluster 0.1.0 (test only)

## Context

The multiprocess tests must use separate OS processes. Two Elixir processes or
multiple Tursox connections inside one BEAM do not prove Turso's inter-process
WAL locking, snapshot, sidecar, crash-recovery, or checkpoint behavior.

The original fixture satisfied that requirement by running this command for
nearly every database operation:

```text
mix run --no-compile bin/multiprocess_probe.exs ...
```

Every command started a complete BEAM OS process, initialized Mix and Elixir,
loaded Tursox and its NIF, performed one short operation, and exited. The two
multiprocess test files performed approximately 18 VM launches. Most operations
took milliseconds after startup, so repeated VM initialization dominated their
runtime and added scheduler/thread pressure when ExUnit ran suites concurrently.

Disposal remains valuable for probes that may crash or corrupt the native
runtime. It is unnecessary for ordinary, explicitly closed multiprocess-WAL
operations.

## Decision

Use one lazily started, suite-owned DevCluster containing two hidden local BEAM
peers for the multiprocess test files.

- `DevCluster` is an exact, test-only dependency with no transitive packages.
- The test alias defers application startup until long-name Erlang distribution
  is available.
- The multiprocess helper owns two peers for the suite and exposes bounded RPC
  operations through a compiled test worker.
- Tests alternate operations between the two peers and continue using unique
  temporary database paths. Concurrent reader/writer and writer/writer cases
  use both peers at the same time.
- The two multiprocess modules are synchronous because they share this
  two-member cluster. Other independent ExUnit modules remain asynchronous.
- The crash-recovery test still sends `SIGKILL` to one real peer. DevCluster then
  starts one replacement peer, and that new OS process performs recovery.
- The command-line probe remains as a thin entry point to the same worker, so
  repository-owned manual probing and capability proof paths remain valid.
- Peer startup, RPC, barriers, process death, and shutdown all have short,
  explicit deadlines. Ordinary waits fail in 2.5–5 seconds, and ExUnit applies
  an eight-second per-test ceiling.
- Warm peers are stopped before the suite-wide native-resource assertion.

The generated-column, custom-type, materialized-view, and hazardous-checkpoint
probes remain disposable `mix run` processes. Their process churn is deliberate
fault containment and is outside this decision.

## Consequences

The multiprocess contract remains stronger than an in-VM simulation: every
participant still has its own BEAM, native runtime, NIF resource table, and OS
process identity. Reusing peers only amortizes startup.

The normal path launches two peers instead of approximately 18 one-shot VMs.
The crash test adds one necessary replacement, for three peer launches across
the complete multiprocess suite. Database and connection resources must be
closed after every remote command because VM exit no longer provides routine
cleanup.

EPMD and local Erlang distribution are now test prerequisites on supported
64-bit Unix systems. Node names are generated by DevCluster to avoid collisions
between concurrent CI test VMs. Hidden peers prevent unrelated local clusters
from merging global registries.

## Alternatives considered

### Keep disposable `mix run` commands

This provides excellent isolation but spends most multiprocess-test time
booting VMs that execute safe, short operations. Rejected for routine WAL tests;
retained for hazardous probes.

### Use Elixir processes in the main BEAM

This is faster but does not exercise OS-process coordination and would weaken
the tested capability claim. Rejected.

### Build a custom persistent port protocol

Two hand-written helper daemons could remain warm, but this duplicates node
startup, RPC, monitoring, replacement, and cleanup already provided by OTP
`:peer` through DevCluster. Rejected.

## Verification

On the development machine, the two multiprocess files dropped from roughly
8.9 seconds of serial traced execution to about 0.8 seconds together. A full
97-test ExUnit run completed in about 3.7 seconds after the change. Exact CI
numbers vary with runner and cache state; `bin/qa_check.sh` records the
acceptance timing.

Acceptance requires:

1. all multiprocess access and recovery scenarios pass with real peer nodes;
2. the killed-peer scenario creates and uses a replacement node;
3. no wait can hang indefinitely;
4. repeated full-suite runs remain green; and
5. all stages of `bin/qa_check.sh` pass.
